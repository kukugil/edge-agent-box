# 托盘里选回复白名单：方案（v2，已吸收 Codex 只读审核）

11/20 用户提出。v1 经 Codex 对照源码审核，**文末"v2 修订"和前文冲突时以 v2 为准**。分支 `codex/tray-v2`，工作树 `D:\Newitem\edge-agent-s3`。

## 要什么

在托盘主窗口的微信页里，勾选哪些微信好友可以自动回复；也能按分组一次勾一批。不用再手改 `agent/test_contacts.local.json`。

完成条件（实测）：

1. 托盘里能看到候选好友列表，可搜索、勾选、按分组整组勾选，保存后重新开始自动回复即生效。
2. 列表里**不出现任何群聊**；群聊即使被手写进文件，保存和启动时也会被拒绝。
3. 同名、读不到、微信没开时，界面写明原因，不静默失败。
4. 读好友列表的过程不和人抢鼠标（见第 5 节）。
5. 原有离线测试全部通过，白名单好友真机回复一条。

## 1. 现状

- 白名单是本机文件 `agent/test_contacts.local.json` 里的 `allowed_chats`（按会话标题，也就是备注名或昵称），另有 `allowed_mail`。
- `trigger.py`、`graph.py` 在**导入时**读一次文件，所以只有重新启动监听进程才生效。
- 发送前已有护栏：会话行要唯一、被选中、标题一致（`WeChatUIA.unique/selected`、`_safe_target`）。这几条不动，白名单只决定"候选名单"。

## 4. 分组

- **托盘自己的分组**（第一版）：用户在托盘里建组（如"测试好友""家人"），组里放已选好友。勾组 = 勾组内全部人。存在本机文件里，不碰微信。

## 5. 前置问题：自动回复和人抢鼠标（11/20 用户实测）

托盘日志 `listen-1120-193338.log`：启动后 30 多秒内两次"没读到会话"，随后用户停止。代码里有三处会在人正在用电脑时动手：

1. **微信在前台时不看人在不在用**：`wechat_reply_flow.Listener.run` 只在"微信不在前台"时才等键鼠停 60 秒；微信在前台就直接点会话、滚列表、粘贴。人在看微信时会被抢。
2. **一轮操作中途不让**：`process()` 一轮包含打开会话、等来信稳定、调模型、发送，几秒到十几秒，中间不检查有没有真人输入。
3. **"还在程序手里"的判断会被程序自己的点击骗过**：`idle_seconds()` 用 `GetLastInputInfo`，程序自己的 SendInput 也会清零（日志里"0 秒没人碰键鼠"就是这条快路径）。

成熟做法：低级鼠标/键盘钩子里看 `LLMHF_INJECTED` / `LLKHF_INJECTED` 标志，带标志的是程序注入的，不带的才是真人（微软 `MSLLHOOKSTRUCT` 文档）。钩子回调要放专用线程、立刻返回，否则会被系统静默摘掉。

建议做法（另开一项，不和白名单混在一次改动里）：

- 监听进程里开一个只记时间的钩子线程，提供"最近一次**真人**输入时刻"。
- 每个会动键鼠的动作前（点会话、滚动、粘贴、回车）检查：真人 N 秒内碰过 → 放弃本轮，草稿按现有规则处理（未粘贴就丢弃，已粘贴保留并转人工，不按回车）。
- 微信在前台时也要先满足"真人停手 N 秒"，N 待定（建议 5 秒，和 UFO 接管一致；60 秒只用于"把微信切回前台"）。
- 白名单的"刷新好友列表"同样走这套让出规则。

## v2 修订（Codex 审核意见，以此为准）

Codex 对照源码静态核对，未操作微信、未读名单内容。Claude 抽查了其中两条（`wechat_uia.py` 只有 `session_item_`；托盘待办名单在 `desktop.py:39` 启动时固定），属实。

### A. 抢鼠标：补充原因和挂点（改第 5 节）

补充的原因：

- **启动就抢前台**：`listen.bring_up` 先把微信切到前台并打开第一个会话，之后才核对唯一（`listen.py:49`、`wechat_reply_flow.py:232`）。人点了"开始"后马上去干别的，会被拉回来。
- `_ours` 有 0.5 秒容差，而且交接时刻记在**一轮结束时**，轮内的真人输入会被掩盖（`wechat_reply_flow.py:294`）。
- `idle_seconds()` 在 API 失败时也返回 0（`window.py:263`），日志"0 秒"不能单独当证据。
- 实际键鼠走 `mouse_event/keybd_event`（`agent/tools/inputs.py:108、131、208`），同样带注入标志，钩子方案成立。

钩子放**监听子进程**，在 `bring_up` 之前启用：动作前直接查时间，独立命令行运行也能覆盖。托盘里的"刷新好友列表"另加同样的门槛。

每次动键鼠前都要过门槛的地方：

| 位置 | 动作 |
|---|---|
| `Listener.run` / `process`、`trigger.prepare` | 轮开始、切前台 |
| `activate` | 还原窗口、Alt 抢前台 |
| `WeChatUIA.open` / `_scroll_to` / `focus_input` / `write` / `clear` | 点会话、滚动、聚焦、粘贴、清草稿 |
| `send.deliver` | 回车 |
| `find_mail` | 还原邮箱窗口 |
| `MailWatcher._front` / `_tap` / `_folder` / `_deliver` | 切页、回收件箱、发后切页、粘贴、读回按键 |

`start_simulation` 只读并标边界（`trigger.py:164`），不用加。

门槛不过时：还没粘贴就放弃本轮；**已粘贴就保留草稿并转人工，不按回车**。

### B. 身份核对（改第 3 节）

现有护栏不够当白名单的身份证明：

- `unique` 只数当前控件树，滚动找到第一个就停；`selected` 只验选中。
- `preview` 返回的是消息原文，不能拿来做身份判断，候选读取时也不要存它。
- 候选缓存只说明"上次见过这个名字"，不能证明是那个人。

改为：只读核对，项目包括通讯录"联系人"分区、控件类型、跨页同名、以及能验证的稳定账号标识；并和目标会话对照。手动输入的名字也要过这一关，查不清就拒绝。具体拿哪些字段，由第 7 节实验 1、2 决定。

### C. 保存、生效和校验时机（改第 6 节）

- **监听运行中禁用"保存"和"刷新"**，和邮箱开关一样（`main_window.py:413、433`）。原因：运行中的微信名单是导入时读的旧名单（`trigger.py:42`），要重启才换；邮件发现用启动快照，晚导入的发送校验却可能读到新文件（`mail_flow.py:88、252`、`mail_nodes.py:34`），名单会前后不一致。
- 托盘的待办名单也在启动时固定（`desktop.py:39`），保存后托盘界面也要刷新。
- 启动校验要放在 `bring_up` **之前**：类型、空名、规范化后撞名、身份。目前只查名单为空和撞名（`listen.py:28`），坏 JSON、缺键会在导入时直接报错，要改成明确提示。
- 原子写入，并原样保留 `allowed_mail` 和其他不认识的字段。

### D. 优先级（改第 8 节）

1. 逐动作让出（A），粘贴后保留草稿转人工。
2. 启动前验身份（B、C 的启动校验）。
3. 运行中禁用保存和刷新，原子写，保留 `allowed_mail`。
4. 白名单界面第一版：候选来源和群聊区分以实验 1、2 结果为准。
5. 标签导入推迟到演示之后。

## 11/20 实验记录：通讯录页和"通讯录管理"窗口（Claude，只读）

条件：微信 4.1.15.56，读屏标志已开。全程只读控件树，没有点击、滚动或输入（"通讯录管理"由用户手动打开），输出里名字全部打码。脚本放在会话临时目录，不进项目。

**通讯录页**（主窗口 → 通讯录）
- 列表 `mmui::StickyHeaderRecyclerListView`，`AutomationId=primary_table_.contact_*`。行类有：`ContactsCellMangerBtnView`（通讯录管理按钮）、`ContactsCellGroupView`（分区）、`ContactsCellClassifyView`（字母）、`ContactsCellItemView`（联系人）。
- 分区：新的朋友、公众号和服务号、企业微信联系人、我的企业、联系人（598）。**没有"群聊"分区**，联系人分区里只有好友。
- 联系人行**没有 AutomationId**；是回收列表，一屏约 9 行。

**通讯录管理**（独立顶层窗口，类 `Qt51514QWindowIcon`，标题"通讯录管理"）
- 左栏：全部（589）、筛选、朋友权限、标签、最近群聊。
- 右栏：表头三列"昵称 / 备注 / 标签"，列表 `mmui::ContactsManagerDetailView`，行 `mmui::ContactsManagerDetailCell`，一屏 10 行。
- 每行**没有子控件、没有 AutomationId**，Name 是一整串"昵称 备注 标签"，用单个空格拼接，空字段留空。10 行里 7 行刚好 2 个空格，能拆开；3 行的名字本身带空格，**拆不准**。
- 列表**不支持 ScrollPattern、Grid、Table**。读全部 589 人只能用滚轮，约 59 屏，期间要占用鼠标。

**结论**
1. 能读到"昵称、备注、标签"三列，标签可以作为分组来源，这一点比通讯录页强。
2. 三个缺口：没有稳定标识（同名分不出）、带空格的名字拆不准、没有不动鼠标的滚动方法。
3. 拆不准的缓解办法：先点左栏"标签"读出全部标签名，再用已知标签名从行尾匹配；或者点某个标签只看该标签下的人。这两步都要点击，属于下一轮实验，要用户同意。
4. 群聊不在这两个列表里，"群不碰"可以靠"只从这里取候选"来保证；"最近群聊"那一栏不读。
5. 联系人页显示 598，管理窗口显示 589，相差 9 人，原因未查。

### 第二轮（用户同意后，用 UIA Invoke，不动鼠标）

- 左栏格子都声明支持 Invoke / SelectionItem / LegacyIAccessible。**更正**：第一次"用 Invoke 展开标签"其实是用户事先已经展开了，不是 Invoke 起的作用。用户重开窗口后（标签处于收起状态），Invoke、Select、DoDefaultAction 三种方式都**没能展开**"标签"。所以"切换筛选不占鼠标"不成立，至少展开这一步不行。每次调用前后鼠标位置都变了，可能是用户在动鼠标，无法区分。
- 对标签行调用 Invoke 能否切换筛选，只试过一次，没有读到结果。
- "标签"下有 3 个标签行 `ContactsManagerControlLabelCell`，Name 是"标签名 + 人数"，能拆开，人数是 515、45、33。另有一行 `ContactsManagerControlCreateLabelCell`（新建标签），不能触发。

- 随后"通讯录管理"窗口不在了，多了一个图片预览窗口（`mmui::PreviewLayer` / `PreviewImage`）。脚本只对标签行调用过 Invoke，没有点其他控件，这两个变化的原因还没查清。已停止，没有再操作。

## 11/21 会话列表滚到底后漏掉来信（新问题，Claude）

- 现象：用户把微信会话列表滚到底，用文件传输助手发消息，自动回复没反应。日志 00:21:48 之后没有任何记录，说明不是"发现了没回"，而是根本没发现。
- 原因（已核实）：会话列表是回收列表，滚出可见范围的行不在控件树里（只读核对：`session_item_文件传输助手` 当时不存在）。发现来信靠两样：截图上的会话行红点、控件树里会话行预览的变化，都要求那一行可见。新消息会把会话顶到列表最上面，可列表停在底部，所以一直看不到。
- 用户发现：快速双击左栏绿色气泡，会话列表会滚到相应位置。实测（程序双击，只记位置、会话名用哈希）：列表在底部、文件传输助手不可见 → 双击 1 次后，列表首行贴着列表顶，文件传输助手是第 1 行，**没有打开任何会话**，前台仍是微信；再双击 2 次，位置不变。读屏接口做不了双击，要用鼠标。
- 待定修法：监听发现列表不在顶部（首行不贴列表顶，或白名单会话都不可见）时，等真人停手（用 `human_input` 钩子），双击气泡回到顶部。
- 已接进自动回复（离线通过，未真机）：`WeChatUIA.at_top()` 判断第一行是否贴着列表顶；`back_to_top()` 双击气泡（点前核对气泡露在外面、属于这个微信窗口，点完鼠标放回原处）。监听每 5 秒查一次，列表不在顶部时：微信在前台就等真人停手 10 秒，被挡住就等 60 秒并先切前台，再双击；拉不回 30 秒后再试。真人停手由 `human_input` 钩子判断。发送前找会话行的 `_scroll_to` 也改成先双击回顶（原来"往上滚 15 格 × 3 次"回不到顶，00:20 那三次"无法唯一定位"可能就是这个原因）。新增 `agent.demos.test_keep_top` 7 项；reliable_reply、mail_flow、send_flow、d16 三组、input_guards、reply_tiers、act_route、whitelist 均通过。
