# 邮件多邮箱接入：方案对比

11/24，Claude 汇总，Codex 独立评估（只读代码，未联网、未碰邮箱）。只讨论，未实施。

## 一、为什么要改

现在的邮件链路靠"读网页控件树"：

- 发现新信慢：列表不会自己刷新，要等标题提醒或每 2 分钟切一次文件夹，再等键鼠停 60 秒，前后要 1–3 分钟。
- 认信脆弱：窗口宽窄会切换版式，名单只能对昵称。
- 只读预览：长邮件只看到开头，回复是否得体没验证过。
- 只认 QQ 邮箱网页：换一家邮箱，整套网页适配要重写。

## 二、先查清的前提

| 项目 | 结论 | 来源 |

| 网易企业邮 | 有"客户端授权密码" | 高校文档和第三方资料，未找到官方页 |
| Outlook / Exchange Online | 收信早已不能用账号密码，必须走微软 OAuth；发信的账号密码登录 2026 年 12 月底默认关闭 | 微软官方 |

## 三、开源项目调研（11/24，Codex 读源码，Claude 抽查）

五个仓库浅克隆到本机临时目录，只读源码，没有运行。Claude 抽查了 6 处关键说法，全部和源码一致（见表下"抽查"）。

| 仓库（版本） | 怎么发现新信 | 怎么起草 | 怎么防错 | 许可证 |
|---|---|---|---|---|
| EmailOps（d4f865b）桌面端，支持通用 IMAP | IMAP IDLE；断线重连后先补查，连接期间每 5 分钟补扫；按 Message-ID 对齐 | 去引用和签名；提示词上限 12,000 字，目标邮件最多 6,000 字，旧邮件先删；要求不编造事实、价格、日期、承诺，缺的用方括号标出 | 发件箱原子领取；重启时发现"发送中"标为中断，提示先查「已发送」，不自动重发 | Apache 2.0，可借代码（Rust） |
| Mail-0 Zero（4b642df）支持 IMAP | IDLE 加每分钟同步；按文件夹记 UIDVALIDITY + UID 进度，批次做完才推进 | 自动只存草稿；不加无依据的承诺；正文长度没上限 | 收件人从 Reply-To/From 算；一次审批只能发一次；SMTP 部分收件人被拒时，上层可能仍报成功（缺陷） | MIT，可借代码（TypeScript） |
| Inbox Zero（ea6bd36）Gmail/Outlook | Gmail 推送、Outlook 通知，每小时续订；Outlook 漏信补查最多 100 封 | 最近一封 2,000 字、之前每封 500 字；允许替用户"猜最可能的答案"（只适合人审草稿） | 每次发送带固定操作 ID，结果不明标 UNCERTAIN，同 ID 不再发；失败重试明确排除发信 | AGPL + 额外条款，5 人以上组织商用受限，**只借思路不拷代码** |
| executive-ai-assistant（758db71）只支持 Gmail | 每 10 分钟查一次，回看 60 分钟 | 模型三分流（不理 / 通知 / 起草）；缺信息就提问；不经同意不答应见面 | 人工确认后才发；没有结果不明状态，也没有防重发 | MIT |
| agents-from-scratch（603fc7a）只支持 Gmail | 每 10 分钟查一次；"已处理过就跳过"留着 TODO 没实现 | 同上三分流；只喂当前一封，不截断不去引用 | 人工确认后才发；没写 In-Reply-To | MIT |

抽查（Claude 直接读源码确认）：EmailOps `services/emails/drafts.rs` 的 12,000 / 6,000 上限和"不编造事实、价格、日期、承诺"提示词；EmailOps `services/outbox.rs` 的 `recover_interrupted_outbox`；Zero `lib/driver/imap.ts:355` 的 `waitForInboxChange`（IDLE，测试覆盖"服务器不支持"）；Inbox Zero `reply-tracker/generate-draft.ts:207` 的 2,000 / 500 字；agents-from-scratch `run_ingest.py` 的去重 TODO；Inbox Zero `LICENSE` 的 5 人以上限制。

**结论：**

1. 五个项目里，**没有一个自动发信是默认开着的**。成熟的都是"程序写草稿，人点发送"，或者"人批准一次，只能发一次"。
2. 最值得借的两个是 **EmailOps 和 Zero**，正好都支持通用 IMAP：
   - 收信：Zero 的进度记录（账号 + 文件夹 + UIDVALIDITY + UID，批次做完才推进），加上 EmailOps 的"启动、重连、定时补扫都走同一个补查入口"。
   - 长邮件：EmailOps 的做法，先去引用和签名，再按目标邮件优先、旧邮件先删的方式分配长度；提示词禁止编造，缺的事实用方括号标出。**我们自动发信时，回复里只要出现方括号就转人工。**
   - 发信：Zero 的收件人计算和"一次审批只发一次"；EmailOps 的发件箱和"中断不重发、先查「已发送」"；Inbox Zero 的"固定操作 ID + 结果不明"这个思路（只借思路）。
3. 分流用 executive-ai-assistant 的三类：不理、通知本人、起草。
4. **五个项目都没有中文引用和签名的识别**，这部分要自己写、自己测。五个项目也都证明不了 QQ、腾讯企业邮、网易企业邮在同一套配置下能工作，要逐家实测。
5. 依赖：Python 标准库（email、imaplib、smtplib、sqlite3）就够用，IDLE 另用 imap_tools。EmailOps 是 Rust、Zero 是 TypeScript，只能照着思路写，不能直接调用。

## 四、两个方案

### 方案 A：协议收信，网页里回复

收信走 IMAP：IDLE 唤醒，读全文，按 Message-ID 去重。回复仍由程序在网页邮箱里点"回复 → 粘贴 → 发送"，沿用现有的网页发送和核对。

- 代码量：新增约 750–1,150 行，改动 180–300 行，测试 240–400 行。**每多一家邮箱，再加 180–350 行网页适配代码。**
- 好处：
  - 发现新信快，能读到全文和完整发件地址，解决延迟、长邮件和昵称这三个问题。
  - 演示时仍能看到"程序在操作电脑回信"，符合项目主题。
  - 某家邮箱只开放收信、限制 SMTP 发信时，这个方案仍可用。
- 坏处：
  - IMAP 找到的信，程序还要在网页上证明"点开的是同一封、同一个账号"。现在靠发件人、标题、预览来对，同名同标题的信就分不清。
  - 发送后的核对只看「已发送」最上面几行，排除不了本人同时发了同标题的信。
  - 每家邮箱的网页都要单独写一套、单独验收，网页一改版就会坏。
  - 仍要等键鼠空闲才能回，还会抢屏幕。

### 方案 B：协议收发

收信走 IMAP，发信走 SMTP，并带上 In-Reply-To / References 头，让回信串在原邮件下面。发出后去「已发送」按 Message-ID 查副本。屏幕只用来展示和人工接管，不点网页。

- 代码量：新增约 800–1,250 行，改动 160–280 行，测试 300–450 行。**能用授权码收发的邮箱（QQ、腾讯企业邮、网易企业邮等）基本只要加一份配置。** Outlook/Exchange 的 OAuth 另算。
- 好处：
  - 发件账号、完整收件地址、邮件 ID 都能由程序逐项核对，比看网页可靠得多。
  - 不抢键鼠，人在用电脑时也能回。
  - 多邮箱共用一份流程，正好满足"工作邮箱不只 QQ"。
- 坏处：
  - 演示时看不到"操作电脑"，邮件这部分就和电脑操作助手的主题脱钩了。
  - 要用户在每个邮箱里开启 IMAP/SMTP，并生成授权码；有的公司会禁用。
  - SMTP 返回成功只说明服务器收下了，不等于对方收到。发送中途断线的结果不明，要转人工，不能自动重发。
  - 有的邮箱发出去后不会自动在「已发送」里存副本，要逐家实测。

## 五、两个方案都必须做的部分（约 600–900 行，占大头）

1. **读全文并分段**：解码正文，分出本轮内容、引用历史、签名和附件信息。分不清，或关键内容在附件里，就转人工。名单按完整地址核对。
2. **邮件专用的分流和起草**：现在的回复内核是给微信短句设计的。它把整封信当成一条消息，会把换行压平，模型输出上限 300 token；全部转人工时，还可能发出一句微信式回执。所以要改成"不理 / 通知本人 / 起草"三类：审批、承诺、付款、重要邀约一律只通知本人；起草保留段落，逐条列出信里的问题和对应答复。**首版只出草稿，在托盘里预览，不自动发。**
3. **多邮箱账本**：现在所有邮件都记在同一个"QQ邮箱"名下，一封信结果不明就会锁住全部邮件。要改成按"账号 + 会话"分开记，另外记下收信进度和发件 Message-ID。
4. **授权码保存**：沿用现在存模型 key 的 Windows 凭据管理器，每个邮箱账号存一条。日志里不写邮件全文。

## 六、建议

**选方案 B 做主线；方案 A 只留给必须经网页发送的邮箱。** Claude 和 Codex 意见一致。理由：

1. 两个方案的工作量差不多，但 B 每多一家邮箱几乎不加代码，A 每家都要重写网页适配。
2. B 能逐项核对"发给了谁、回的是哪封"，A 只能靠看网页猜，安全上差一截。
3. 长邮件写得是否得体，是两个方案共同的难点，跟选哪个无关，要单独做、单独验收。
4. 调研过的五个开源项目里，支持通用 IMAP 的两个（EmailOps、Zero）都是协议收发；没有一个靠操作网页来回信。

要你定的一点：选 B，邮件就不再是"操作电脑"的演示内容。如果演示时仍想展示操作电脑，可以把收发换成 B，再在托盘或屏幕上把"读信 → 草稿 → 核对 → 发出"的过程展示出来。

**今天（11/24）演示不改邮件链路。** 这套改造放到演示之后。

## 七、第一个最小实验（还没做）

只验证协议能不能形成闭环，不碰模型：

1. 准备两个测试邮箱，A 给 B 发一封合成的长邮件，关键请求放在最后一段。
2. B 端用 IMAP 定时轮询取到正文，确认最后一段完整。
3. 用一句人工写好的固定回复，通过 SMTP 回信。
4. 按发件 Message-ID 去 B 的「已发送」找副本；在 A 端核对收到几封，以及回信是否串在原信下面。
5. 重启收信程序再扫一遍，确认同一封原信不会再次登记。

通过线：正文完整、收件人唯一、回复串在原信下面、只发一封。这个实验要用户提供一个隔离的测试邮箱，并自己生成授权码。
