## 一、结论先说

1. **ufo2 分支的问题不在"点不准"，而在"步骤归模型管"。** 计算器反复"点 1 → 清除"、浏览器反复重观察，都是模型每一步自由重排计划，程序只能事后拦。Codex 加的进度监控能拦住错误，但拦不出正确的下一步（已按"修两次不好就停"停手）。
2. **改法：进度归程序管。** 规划模型一次性把任务拆成几个"小目标"，每个小目标带一条**程序能核对的完成条件**。执行模型每次只看当前一个小目标，只出一步。小目标达成由程序判定，不问模型；只有程序核对到失败，才允许带着证据重排剩下的目标。
3. **点准靠三级定位 + 点之前回查。** 控件树能找到就用控件框（最准）；找不到用 OCR 文字；再找不到才用视觉模型，并且先粗定位、再裁局部放大定位。无论哪一级，点之前都用 Windows 的"这个坐标下是什么控件"回查一次，对不上就不点。
4. **UFO² 留作工具库，不再用它的主循环。** 它的控件树读取、窗口选择、启动应用这些都好用；HostAgent/AppAgent 的自由调度换成我们自己的 LangGraph 循环（正好是项目原定的"看 → 想 → 做 → 核对"）。
5. **先做三个半天以内的小实验，过了通过线再实施**（见第七节）。

## 二、ufo2 分支现在是什么样

读的是 `codex/ufo2-desktop-assistant` 的已提交代码和未提交改动（12 个文件改动、若干未跟踪文件，本次没动），加上 `reports/desktop-assistant/` 的三份分析。

**已经有的（可以留）：**

- 托盘入口、可切换 API、Windows 凭据存 key、预算账本、人工接管（空闲 5 秒重观察）、和微信共用的跨进程桌面锁。
- 动作护栏：只放行点击、输入、滚动和少数导航快捷键；禁止发送、删除、购买、关闭；点击前查前台窗口和落点窗口；输入前查焦点。
- 从 Windows 应用目录按编号启动应用，启动参数不来自模型。
- 计算器结果、浏览器搜索结果的独立核对器。

**实测结果（DeepSeek，不挑轮次）：** 计算器 4 轮 1 次得到 99（含人工接管），浏览器搜索 3 轮 2 次成功（1 次含接管）、1 次撞 180 秒上限。两项都没达到"连续 3 次无人干预"。

**失败归成三类：**

| 类别 | 现象 | 根因 |
|---|---|---|
| 步骤失控 | 点"1"后又点"清除"，交替循环；漏输入一个 0；把历史记录 99 当当前结果 | 模型每步自由重写计划，"已完成到哪"只存在模型的文字里。程序没有自己的进度状态 |
| 选错对象 | "搜一下深圳的天气"被选成 Windows 天气应用 | 旧版用正则从整句里猜应用（后来已改回 UFO 调度） |
| 观察不稳 | 窗口和输入一变就重建整轮观察，反复到超时 | 一出变化就丢掉整轮 Session 重来，没有"只重看、不重排"的轻量路径 |

点不准没有成为主要失败原因：现在只在控件树里点控件框中心，不点控件树之外的东西。**这也是它的上限**：网页内容、微信、自绘界面、图标按钮在控件树里读不到或没名字，现在的设计直接不能点。所以通用化以后，"点准"会变成主要问题，要提前设计。

## 三、外面是怎么做的

| 项目 | 拆步骤的做法 | 点准的做法 | 借鉴什么 |
|---|---|---|---|
| UFO² / UFO³（微软） | HostAgent 选应用，AppAgent 逐步自由决策；UFO³ 用任务图（DAG）编排多设备 | 控件树 + 视觉解析混合；能调应用 API 就不点界面；一次预测多个动作，执行前逐个对照控件树验证 | 控件树为主；API 优先；多动作预测后统一验证（官方称模型调用少 51%） |
| Agent S3（Simular） | 去掉了"经理—工人"两层，主模型直接出动作，可以写代码代替点界面；多跑几遍再挑最好的一遍（bBoN） | 主模型说"点哪个东西"，UI-TARS-1.5-7B 负责给坐标 | 规划和定位分开（我们已在用）；能用代码/快捷键完成的不点界面 |
| Mobile-Agent-v3.5 / GUI-Owl-1.5（阿里） | 经理（规划）、工人（执行）、反思者（核对）、记录员（记中间结果）四个角色 | 自带"裁剪放大"工具：带裁剪时 ScreenSpot-Pro 80.3，不带 72.9 | 定位前先裁剪放大；单独的核对角色 |
| Windows Agent Arena 的 Navi | 单模型逐步 | 控件树 + OmniParser 混合比纯视觉成功率从 12.5% 提到 19.5% | 控件树和视觉一起给，比只给一样好 |
| GUI-Critic-R1 | 动作执行前让一个小模型先判断"这一步对不对" | — | 点之前查一次，比事后补救便宜 |
| RegionFocus、UI-Zoomer 等 | — | 不确定时才放大局部重新定位；一律放大反而可能变差、变慢 | 放大只在没把握时做 |
| cua-driver、dsh-cua 等 MCP 工具 | — | 控件树优先，截图兜底；"控件树有时会说谎，要两边互相核对"；DPI 缩放会让坐标系混用 | 落点回查；坐标换算只在一个地方做 |

共同点：**规划、定位、核对分成不同角色**；**能不用坐标就不用坐标**；**放大和回查只在没把握时做**。

## 四、方案

![](学习笔记/图/20-通用桌面操作总图.svg)

| 框 | 做什么 | 谁来做 |
|---|---|---|
| 拆成带核对条件的小目标 | 把一句话拆成 2–8 个小目标，每个带完成条件 | 规划模型（大模型），每个任务一次 |
| 读控件树和截图 | 当前窗口的控件列表 + 一张截图（需要时） | 程序（复用 UFO 的 UIA 读取） |
| 只为当前小目标选一步 | 只看当前小目标、它的完成条件、当前界面、上一步结果，出一个动作 | 执行模型 |
| 三级定位 | 把"点哪个东西"变成屏幕坐标 | 程序 + 定位模型，见下一张图 |
| 点之前查落点 | 坐标下的控件和描述对不对得上 | 程序；对不上时最多重新定位一次 |
| 执行键鼠 | 现有 `Inputs` 和护栏不变 | 程序 |
| 程序核对小目标 | 按完成条件判断，达成就进下一个目标，不问模型 | 程序；条件写不出时才用视觉模型判断 |
| 带失败证据重排剩余目标 | 只重排没完成的部分，已完成的不许推翻 | 规划模型 |
| 停下交给人 | 同一个小目标第二次失败、或碰到禁止动作 | 程序 → 托盘 |

### 4.1 拆步骤：小目标 + 完成条件

规划模型输出类似这样的结构（示意）：

```json
{"subgoals": [
  {"goal": "打开计算器", "done_when": {"window_process": "CalculatorApp.exe"}},
  {"goal": "输入 100-1=", "done_when": {"control": {"automation_id": "CalculatorExpression", "name_contains": "100"}}},
  {"goal": "读出结果", "done_when": {"control": {"automation_id": "CalculatorResults", "number": 99}}}
]}
```

要点：

- **完成条件用一小套程序能判断的写法**：窗口进程/标题、某控件存在、控件文字或值、地址栏参数、OCR 看到某段字。实在写不出才用 `{"judge": "描述"}` 交视觉模型判断，并且在结果里标成"弱证据"。
- **进度存在程序里**（LangGraph 状态）：当前第几个目标、每个目标试了几次、上次失败的证据。执行模型拿不到"整个计划"，也就没法自己把已完成的推翻。计算器那种"点完 1 又清除"在结构上就出不来。
- **重排只在程序核对失败后发生**，输入是"哪个目标、期望什么、实际看到什么"，只允许改剩下的目标。
- **一个小目标里可以一次出多步**（UFO 的多动作预测）：比如"输入 100-1="一次给出 6 个按键，程序先逐个对照控件树确认都存在，再连续执行，最后核对一次。省模型调用，也省时间。
- 应用选择由规划模型从已核对的应用目录里选，不用正则猜；有歧义（比如"浏览器"有两个）就问用户。

### 4.2 点准：三级定位 + 落点回查

![](学习笔记/图/21-三级定位细节.svg)

| 级别 | 什么时候用 | 坐标从哪来 | 预期准度 |
|---|---|---|---|
| 1 控件树 | 目标有名字/类型/编号且唯一 | 控件框中心；滚到可见再取（ScrollIntoView） | 最高，几乎不会偏 |
| 2 OCR | 目标是可见文字，但控件树没有（网页正文、微信、自绘界面） | 文字框中心 | 高；同名文字多个时要靠区域限定 |
| 3 视觉模型 | 图标按钮、没文字的元素 | 先整屏粗定位，再以粗定位点为中心裁一块放大到原尺寸再定位 | 取决于模型，要实测 |

点之前的回查（"点之前查落点"）：

- **控件回查**：用 UIA 的"这个坐标下是什么控件"（ElementFromPoint），看名字、类型和描述是否一致，再看它属于目标窗口。这一步几毫秒，三级都做。现有代码已经查"落点属于哪个窗口"，这里细到控件。
- **看图回查**：控件回查给不出信息的界面（微信大部分区域、画布），截落点周围一小块画上十字，问视觉模型"十字是不是在 X 上"。只在第 3 级、或者这一步有风险时做。
- 对不上就换下一级或者放大重定位，最多一次；还不行算定位失败，交给重排。

坐标和 DPI：进程开每显示器 DPI 感知，截图、控件框、鼠标坐标统一在一个函数里换算（现在的 `shot.to_screen`），不在别处各算各的。

### 4.3 动作优先级

能不用点的就不点：

1. **系统和应用自带的入口**：按应用目录启动、地址栏直接输网址、应用快捷键（Ctrl+L、Ctrl+F 等，仍走允许清单）。
2. **控件操作**：控件树定位后用真实鼠标点、粘贴输入。
3. **坐标点击**：只有 OCR 和视觉定位的结果，必须经过回查。

是否用 UIA 直接"按按钮"（InvokePattern）代替真实点击，见第十节待定问题。

### 4.4 复用：跑通一次就存成做法

任务成功后，把"小目标 + 每步用的定位条件（控件名/类型/文字，不存坐标）+ 完成条件"存成一份做法。下次同类任务换参数，先按做法重放，每个小目标照样核对；哪一步对不上，只从那一步开始交回模型。这就是 11/11 "探索后固定"实验想验证的东西，那次被网络权限拦下没跑成，可以在这套结构里一起验证。

### 4.5 安全护栏照旧

现有的禁止清单、接管、桌面锁、180 秒和 30 动作上限、窗口绑定都保留。新增两条：小目标的完成条件不能由模型自报；重排不能推翻程序已核对通过的目标。

## 五、模型按角色选，可以换

| 角色 | 要求 | 候选 | 备注 |
|---|---|---|---|
| 规划（拆目标、重排） | 理解力强，次数少（每任务 1–3 次），慢一点可以 | 云端大模型；或本地更大的 Qwen | 用户说后面可以换大模型，这里收益最大 |
| 执行（每步选一个动作） | 快，结构化输出稳 | Qwen3.8-27B（关思考）、DeepSeek | 只看一个小目标，难度比现在低很多 |
| 定位（第 3 级） | 坐标准，越快越好 | 现有 UI-TARS-1.5-7B；候选 GUI-Owl-1.5-8B、UI-Venus-1.5-8B（公开 ScreenSpot-Pro 分数明显更高） | 公开分数只作线索，要在我们的界面上实测，见实验二 |
| 核对（弱证据、看图回查） | 能看图，回答"是/不是" | 规划或执行模型兼任 | 只在程序判断不了时用 |

模型接口按角色配置，换模型只改配置。

## 七、先验证：三个小实验

每个限半天，都不碰微信、不发送任何东西；截图存 `%LOCALAPPDATA%`，不进项目。

| # | 验证什么 | 怎么做 | 通过线 |
|---|---|---|---|
| 1 | "小目标 + 完成条件"能不能管住步骤 | 用 11/16 计算器、浏览器失败轮次保存的界面，离线回放：规划模型拆目标，执行模型只看当前目标出动作。2–3 个模型各跑 5 遍 | 完成条件能被程序判断的 ≥ 80%；没有出现"无失败证据就清除/重来"；在当时出错的那一步给出正确动作 ≥ 4/5 |
| 2 | 第 3 级定位在我们的界面上有多准 | 在计算器、记事本、设置、资源管理器、Chrome 上自动截图，用控件树的框当标准答案（不用人工标）。去掉控件树，只给截图和描述，比 UI-TARS-1.5-7B 和 1–2 个新模型，带/不带放大 | 带放大命中框内 ≥ 95%；单次定位 ≤ 3 秒；选出一个定位模型 |

三个都过，再按第四节实施，然后跑第八节的任务集。任何一个不过，带着数据回来讨论，不硬上。
